# 毁伤→能力降级（三杀模型）技术方案

> 草案 v0.1（2026-10-17）→ **v0.2 已拍板并实现**：按类统一设置 = platform_type
> 继承下发（零新机制）；未配置 = 不降级直到完全损毁。正式记录见
> `00-框架设计.md` §5.17.11（v0.13.65），本草案留档。

## 0. 一句话

存活期间挨打会**掉能力**而不是只掉血条：完好度跌破阶梯阈值后，机动/火力/探测
三个通道独立降级（装甲兵"三杀"分类：M-kill / F-kill / S-kill）。默认关，
老想定逐位不变。

## 1. 动机与适用判据

**现状**（§5.17，v0.13.54 点数制）：命中 → 扣血量点数 → store 完好度（0..1）→
`is_alive` 二值。完好度 (0,1) 的中间状态**不影响任何行为**——唯一消费者是
Mover 的 `my_alive()` 早退（残骸停推）。坦克挨一发还剩 70% 血，照样全速跑、
照常开火、雷达满功率，账上等于没挨。

**适用判据：代偿裕度 = max_health / 典型单发伤害 ≥ 2~3。**

- 船（血条厚、多命中存活）与装甲车（M-kill/F-kill 是真实战术概念）自动入选；
- 导弹（一发即死）、软皮车（默认 max_health=1.0，一发归零）的存活状态集合
  只有"完好/摧毁"两个点，降级曲线没有插值余地，**不建模就是正确答案**；
- 用判据而不是类别清单：新想定不用维护"谁适用"的表，max_health 低的目标
  天然落在"永远不会降级"的档位里。

**落地方式：想定显式启用，不做自动判定。** 平台挂一个 `degradation` 参数
（默认空 = 关）。自动按 max_health 推断看似省事，但"这一发打掉 60% 算不算
重损"本质是装备设计的表态，交给想定作者拍板更干净。

## 2. 模型：三通道阶梯

完好度 r ∈ (0, 1]（r = store 完好度），三档阈值 a > b（默认 a=0.5、b=0.2）：

| 档位 | 条件 | 机动 mobility | 火力 firepower | 探测 sensor |
|---|---|---|---|---|
| 完好 | r > a | 100% | 正常 | 0 dB（不折） |
| 重损 | b < r ≤ a | 60% | 半射速 + reload 耗时 ×2 | −6 dB |
| 瘫痪 | 0 < r ≤ b | 25% | **拒发**（F-kill） | **关机**（S-kill） |
| 摧毁 | r = 0 | —（残骸，现状不变） | — | — |

**阶梯而不是线性**，理由有三：①真实装备降级是分级的（轻损/重损/瘫痪），
线性缩放会把"断了一条履带"稀释成"慢了 3%"这种没法裁决的中间态；②每档一个
确定数值，测试有逐位锚点，AFSIM 对拍有确定输入；③线性会让所有依赖
`max_speed` 的既有锚点测试失去意义。

**阈值与档值可配**，默认表只是预置档。想定两种写法：

```
platform 装甲车
   degradation armored          # 引用内置档（armored / naval）
# 或逐项覆盖：
   degradation_thresholds 0.6 0.25    # numbers，两档阈值
   mobility_scale 1.0 0.5 0.2         # numbers，三档速度比例
   sensor_penalty_db 0 -8 off         # strings，三档探测折扣（off=关机）
```

装配校验：阈值严格降序且落在 (0,1)；比例全在 (0,1]；每档 2~3 个值；
`degradation` 引用未知名报错。**错即装配期报错**，与 `route` 空表同一风格。

## 3. 注入点（每通道一处，不散落）

### 3.1 机动（M-kill）
`mover/base.py` 读 `max_speed` 的唯一出口处乘 mobility 档比例（1139 行附近
`base = float(self.spec["max_speed"])`）。加速度/油料烧率**不动**——少一环
记账，速度档已表达"能动但慢"。

### 3.2 火力（F-kill）
`weapon/base.py` 开火检查链（现有"弹药耗尽先 reload"拒绝的同一条链）加一档：
重损档放行但 reload 耗时 ×2；瘫痪档拒绝，`bus.command_rejected(实体, 指令,
"firepower_kill")`——v0.13.60 的拒绝事件管线现成，任务层 attack 会自然收到
task_changed(failed)。

### 3.3 探测（S-kill）
`percep/base.py` 的 `snr_at_reference` 上减 sensor 档 dB（重损 −6 dB / 瘫痪
关机 = 恒不探测）。**只动这一个口**：Pd 曲线、探测半径、干扰账全部自然跟随，
不用另记账。关机档实现为探测件 tick 直接早退（与 `my_alive` 早退同一位置）。

### 3.4 读数口
组件**不直接读别人血条**（阵营隔离在感知层，同一规矩）：MoverView 新增
`my_mobility()` 等只读口，内部查 store 完好度 → 查档。store 只加一个
`capability_of(entity_id, channel)` 查询函数，不存第二份状态——档位是
完好度的纯函数，**不缓存、不落账**，`set_damage` 之后下一拍自动生效。

## 4. 语义分家（连带账，必须写清）

- **"丧失战斗力" ≠ "被摧毁"**：`is_alive`（完好度 > 0）语义**不变**——瘫痪
  目标还在编队占位、还能被打、雷达还能看见它、`engagement_resolved` 原样。
- 任务层第一版**不改**：attack 任务把瘫痪目标仍视为有效目标（打瘫痪目标
  有战术价值——封锁港口里的船）。task_changed 的 target_destroyed 只在
  完好度归 0 时触发（现状）。是否给 attack 加"瘫痪即 complete"选项，留待
  用过一版再议（§0 留口）。
- 降级**跨档不广播事件**（第一版）：档位是查询型纯函数，观察口
  `Simulation.capability_of()` 够用；需要"重损瞬间上报"时再加事件族，避免
  现在预支协议。

## 5. 兼容性（基线逐位不变的保证）

- `degradation` 默认空 ⇒ 三通道恒全额 ⇒ 1446 条基线测试**逐位不动**；
- `max_health` 默认 1.0 的老目标即使误配了 profile，一发就归 0，永远走不到
  降级档——双保险；
- 弹（missile mover）装配期禁配 `degradation`（一发即死的目标降级无意义），
  误配报错。

## 6. 测试计划

1. **纯函数**：阶梯表边界逐位钉死（r 恰好 = a / = b 落哪档、r=0 摧毁档、
   覆盖档的装配校验五例）；
2. **机动**：重损档速度锚（降级前后 delta 位移手算对拍）、瘫痪档 25%；
3. **火力**：重损半射速 + reload ×2 计时、瘫痪档拒发走
   `command_rejected("firepower_kill")`、任务层 attack 收 failed；
4. **探测**：−6 dB 档 = snr_at_reference 平移后 detections 数变化锚、
   关机档恒零探测、干扰/假目标账跟随；
5. **端到端**：warhead.txt 式想定改 4 血量目标，两发间隔打击，第二发后
   观察口读 mobility 60% + 弹目几何复核；
6. **回归**：全量 pytest 基线（1446）零位移。

## 7. 本版不做（边界）

- **部位/子系统级**（发动机 vs 履带 vs 炮塔独立账）——L5 部件模型，等三杀
  版跑顺、有对标需求再议；TF 文章 171 的部件依赖归并属于这一层；
- **维修恢复**：resupply 不碰降级（档位纯函数，修血自动升档，无需恢复机制）；
- **线性曲线**：见 §2；
- **降级事件广播**：见 §4；
- **三维空间约束**（爬坡/姿态保持）：milsim 定位 2D 水平面，不采纳。
